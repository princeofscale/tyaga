## 3. Дефекты

### QA-R09-01 · Medium · правка более ранней тренировки того же дня подменяет «Закончил» в комнате — класс: код

Новая в R9 ветка `LiveBroadcastPolicy.afterEdit` (`src/domain/LiveSession.ts`) решает, что правилась «самая свежая тренировка», только по условию `all.some(w => w.id !== edited.id && w.date > edited.date)`. При двух тренировках за один день условие не срабатывает для более ранней, и её итог уходит в комнату вместо итога реально завершённой.

Шаги (A и B в одной комнате, стенд 8801; скрипт `s1c-tie.mjs`, вывод `out-s1c-tie.txt`):
1. У A за 16 нояб. уже есть несколько тренировок (в том числе «Новая тренировка» 50 × 10, 500 кг, 1 из 3 подходов отмечен).
2. A: «Начать тренировку» → «Жим штанги лёжа» 100 × 10 × 3 → «Завершить». В журнале A `PUT /live/state done 3/3 3000 кг`, у B «Игорь · **Закончил · 3 т**» (`qa01-B-before-edit.png`).
3. A: «История» → вторая карточка за 16 нояб. (более ранняя тренировка) → «Редактировать» → вес подхода 1: 50 → 95 → «Сохранить изменения».
4. Через ≈ 8 с после «Сохранить» у B: «Игорь · **Закончил · 1 т**» (`qa01-B-after-edit-of-earlier-workout.png`). В журнале A: после `done 3/3 3000 кг` (13,9 с) на 26,3 с уходит `PUT /live/state done 1/3 950 кг` — итог правленой тренировки.

Ожидаемо: правка не последней по времени тренировки комнату не меняет («Закончил · 3 т» остаётся). Фактически: комната показывает итог правленой тренировки («1/3 подх.», 950 кг → «1 т»), хотя A закончил тренировку на 3 000 кг. До R9 правка комнату не трогала, так что это регрессия новой ветки. Правка тренировки от 6 нояб. (не последней по дате) комнату не меняет: вес первого подхода 61 → 63, `PUT` не уходит, у B прежнее «Закончил · 0,5 т» (`s1d-older.mjs`, `out-s1d-older.txt`) — это работает.
Предложение: пересчитывать итог только для тренировки, завершённой в этой комнате (запомнить её `id` в момент `finish`), либо сравнивать с `updatedAt`/порядком списка, а не только с `date`.

### QA-R09-02 · Medium (вне ТЗ R9, предсуществующее) · вторая вкладка со старым живым черновиком затирает «Закончил» напарнику — класс: код / ТЗ (пробел)

Вероятная первопричина О1 из ТЗ («Закончил · 1,9 т» → «Готовится · Жим штанги лёжа · 0 т» и «не возвращается»): на HEAD мне О1 именно при правке воспроизвести не удалось (раздел 5), но тот же класс симптома стабильно даёт вторая вкладка. Состояние в комнате — одна ячейка на человека, а каждая открытая вкладка со своим живым черновиком шлёт туда свой снимок раз в 45 с (heartbeat), синхронизации черновика между вкладками нет (в коде нет ни `storage`-, ни `BroadcastChannel`-слушателя для черновика; проверено чтением).

Шаги (`s1b-staletab.mjs`, вывод `out-s1b-staletab.txt`): A в комнате, вкладка 1: «Начать тренировку», ✓ подход 1 → вкладка 2 того же браузера: «Сегодня» → «Продолжить тренировку» (на экране 1 / 3, 400 кг, пауза) → вкладка 1: ✓ подходы 2 и 3 → «Завершить» (на 24,5 с, `PUT done 3/3 1885 кг`). У B «Закончил · 1,9 т» на 37,0 / 47,0 / 57,2 с (`qa02-B-after-finish.png`). Дальше без действий:
- 60,1 с — `PUT /live/state resting 1/3 400 кг` из вкладки 2 (через 35,6 с после «Завершить»); у B на 67,2 с «Отдых 0:35 · 1/3», потом «0:25», «0:15», «0:05»;
- 107,3 и 117,3 с — у B «Жим штанги лёжа · 1/3 0:00»; «Закончил» не возвращается (`qa02-B-stale-tab-overwrote.png`). В трёх прогонах перезапись приходила на 58,5–60,1 с.

Ожидаемо: после «Завершить» напарник по-прежнему видит «Закончил». Фактически: через ≈ 36 с старая вкладка возвращает «1/3» (heartbeat второй вкладки). Если во второй вкладке отмеченных подходов нет, по коду вместо этого будет строка «Готовится · Жим штанги лёжа 0 т» (так в ТЗ у PO; этот вариант я отдельно не гонял). Для PO первичен именно этот эффект («единственное место раунда, где другому человеку показываются неверные данные»). Предложение: не слать heartbeat из скрытой вкладки (`document.visibilityState`), слушать `storage` и снимать трансляцию у вкладки, чей черновик уже закончен в другой; ТЗ исключало «синхронизацию вкладок в реальном времени», поэтому решение о блокировке — за lead/PO.

### QA-R09-03 · Medium · чип «Блок / Кроссовер» в «Заменить» пуст для любого упражнения каталога — класс: код и ТЗ неоднозначно

`detectExerciseEquipment` (`src/domain/ExerciseAlternatives.ts`) проверяет `loadMode === "machine_stack"` раньше «блок / канат / кроссовер», поэтому все блоки и кроссоверы (14 упражнений: «Сведение рук в кроссовере», «Тяга верхнего блока», «Разгибание рук на блоке», «Тяга каната к лицу…», …) получают метку «Тренажёр». По всему каталогу метка «Блок / Кроссовер» не получает ни одно из 61 упражнений (по подписям: Штанга 13, Гантели 14, Тренажёр 23, Свой вес 9, «Штанга / тренажёр» 2).

Шаги: «Сегодня» → «Начать тренировку» → «Сведение рук в кроссовере» → «Ещё для упражнения» → «Заменить» → чип «Блок / Кроссовер»: «Анатомические альтернативы с тем же фокусом (0)», «Нет подходящих альтернатив для выбранного инвентаря» (`qa03-390-swap-cable-empty.png`). В «Все снаряды» у того же окна среди 6 строк есть «Сведение в кроссовере с верхних блоков» с меткой «Тренажёр» (`qa03-390-swap-all.png`). Для всех 5 проверенных карточек (жим лёжа, кроссовер, подтягивания, жим ногами, жим гантелей) чип даёт 0, при поиске «жим» тоже 0.

Что требовало ТЗ: О2 прямо перечисляет «Блок / Кроссовер → 0» среди симптомов; критерий 1 — ««Тренажёр» и «Блок / Кроссовер» — все строки с такой меткой из списка «Все» (например, «Сведение рук в кроссовере»)». Это пример строки, которая в «Все» помечена «Тренажёр», то есть ТЗ само не различает два чипа. Формально «ровно строки с этой меткой» выполнено (таких строк нет), по сути чип мёртв и честного «ничего нет» не даёт (в списке строки «в кроссовере» есть). Решение инженера объяснимо, но ожидание PO («нажал — увидел кроссоверы») не выполнено. Вердикт: недоработка по сути, формально в ТЗ ничего не нарушено. Предложение: относить упражнения с «блок / канат / кроссовер» в названии к чипу «Блок / Кроссовер» (проверка раньше `machine_stack`) либо прятать чипы без строк для текущего упражнения.
Дополнительно (Low, по замыслу): по этой же причине в 9 парах «упражнение × чип» чип даёт 0, хотя вне первых десяти альтернатив в каталоге есть подходящие (Гантели 2, Свой вес 3, Штанга 4): фильтр действует только на уже отобранные 10.

### QA-R09-04 · Medium · «Нет связи» при простое и при молчащем сервере появляется намного позже 15 с — класс: код

Критерий 1 REQ05: «сеть выключена: ≤ 15 с в шапке комнаты строка «Нет связи …»». Состояние сети определяется только по неудавшимся отправкам состояния. Если человек между подходами ничего не нажимает, отправка идёт по heartbeat раз в 45 с; неудачные опросы комнаты (`refresh`, раз в 5 с) в счёт не идут.

Шаги: A в комнате, тренировка идёт, 1 подход отмечен; `context.setOffline(true)`; без нажатий. Журнал A: офлайн 14,5 с → первая неудачная отправка 65,3 с → строка «Нет связи …» через 61,9 с после отключения сети (на ≈ 76 с) (`out-s5-idle-390.txt`).
Сравнение: с ✓ сразу после отключения — 11,6 / 12,1 / 11,1 с (390 / 360 / 320); при «молчащем» сервере (запрос висит до тайм-аута 15 с, `s5c-hang.mjs`, вывод `out-s5c-hang.txt`) — 35,3 с после ✓: PUT ушли на 12,1 и 31,1 с и оба оборваны тайм-аутом клиента (15 с), строка после второго обрыва (отчёт инженера эту задержку признаёт). Ожидаемо: ≤ 15 с независимо от нажатий. Предложение: считать неудачи опроса `refresh` и событие `offline`, сократить тайм-аут отправки состояния.
