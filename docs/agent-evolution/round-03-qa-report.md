**QA-R03-01 — офлайн-запуск не работает сразу после первого входа (высокая).**
Сценарий из ТЗ: «войти с сетью → закрыть вкладку → отключить сеть → открыть адрес» (`s7b-firstlogin.mjs`, шаги F1–F4). Профиль для офлайн-входа пишется (`tyaga-offline:session`) только при **следующей онлайн-загрузке страницы**, а не при регистрации или входе.
- F1: сразу после регистрации в `localStorage` есть `tyaga-offline:data:<id>` (330 байт), но нет `tyaga-offline:session`.
- F2: новая вкладка при недоступном API показывает экран «Тяга | Запрос не завершился… | Повторить» вместо приложения. SW при этом контролирует страницу, оболочка в кэше.
- F3/F4: после одной дополнительной онлайн-загрузки ключ появляется, и офлайн-запуск работает (баннер «Нет связи…»).
- Тот же эффект независимо воспроизведён в `s7-security` (S4/S5).
- Последствие: новый пользователь, зарегистрировавшийся и сразу закрывший приложение, при первом офлайн-запуске получает ошибку — именно тот сценарий, который описывает ТЗ.
- Предложение: записывать `tyaga-offline:session` в момент успешной регистрации/входа.

**QA-R03-02 — запуск из программы подставляет придуманные значения (средняя).**
`s10-program-start.mjs`, `s10-program-start-360.png`. Программа «Жим штанги лёжа» + «Тяга верхнего блока», запуск кнопкой «Начать»:
- «Тяга верхнего блока» (истории нет): поле повторов = «10», поле RIR = «2» как введённые значения;
- «Жим штанги лёжа»: подходы 77,5 × 8 / 8 / 8, а «Прошлый» показывает 8 / 8 / 7.

ТЗ R03-REQ02 (а) и (б) прямо говорят, что без истории повторы и RIR не подставляются, а подход N берёт подход N из «Прошлого». В свободной тренировке это выполнено, в запуске из программы нет.
Оговорка: возможно, это сознательно, как «план программы» (в карточке написано «Повторять структуру, брать веса из истории»). Тогда ТЗ нужно уточнить. Что именно запишется в историю, я не доказал: финиш этого сценария блокировал отдельный запрос «Укажи тренажёр для «Тяга верхнего блока»» (штатное правило сравнения машин, `s10b-program-rir.mjs`), значит, «✓ записывает RIR 2» — вывод по значению поля, а не по записи на сервере.

### 2. R03-REQ04 — очередь отправки (`q1-queue.mjs`, `q2-reject.mjs`, `q4-csv.mjs`)

**Основной сценарий (390 и 360, свежая D1, свежая регистрация, настоящий SW).** Регистрация → контроль SW → тренировка «Жим штанги лёжа» (60 × 5 ✓, 62,5 × 4 ✓) → **мой Worker остановлен** (порт не отвечает) → **одно** касание «Завершить тренировку»:

- Экран «История тренировок», у записи метка **«Ждёт отправки»**, баннер «Ждёт отправки: 1 тренировка. Она сохранена на устройстве и уйдёт сама, когда появится связь. [Отправить сейчас]», тост «Нет связи: тренировка сохранена на устройстве и ждёт отправки. Уйдёт сама, когда появится связь.» Черновика нет, на сервере 0.
- «Сегодня»: тот же баннер, метка у записи в «Последних тренировках», «Продолжить тренировку» нет.
- Перезагрузка без сети (SW отдаёт оболочку): «Сегодня» с баннером «Нет связи: показаны данные с этого устройства.» + баннером очереди, очередь (1 запись) и метка в «Истории» на месте, без «Запрос не завершился».
- Вторая вкладка без сети: очередь видна (1 запись, метка).
- Три переключения `setOffline` при остановленном Worker: очередь 1.
- Worker запущен, ничего не трогаю: очередь опустела **через ~18 с** после старта Worker (он начал отвечать через 4–6 с; сработал автоповтор — какой именно триггер, таймер 30 с или другой, я не разделял). Метка и баннер исчезли.
- `/api/data`: **ровно 1** тренировка, `revision 1`, подходы `[60,5,✓] [62.5,4,✓] [62.5,4,не выполнен]`. Прямой запрос D1: **1 строка** с тем же `id`.
- Перезагрузка обеих вкладок + 4 переключения online/offline + две вкладки: на сервере по-прежнему 1, очередь пуста, метки нет. В журнале Worker ровно **один** `PUT /api/workouts 200`.
- На обоих размерах результат совпал (360: тот же `id`-счёт, один PUT).

**Очередь поверх импортированной истории (`q4-csv.mjs`, реальный CSV «Да»).** 21 / 175 / 94 450 кг. «Завершить» онлайн одним касанием (без нативных и DOM-диалогов) → 22 / 178 / 96 232,5; в записи только выполненный жим 77,5 × 8/8/7 (RIR 2), невыполненные «Подтягивания» не попали. Затем «Завершить» при остановленном Worker → метка, перезагрузка без сети → очередь цела → запуск Worker → 23 / 181 / 96 852,5 кг, D1 = 23, в журнале Worker 2 × `PUT` (онлайн-запись и одна из очереди).

**Отказ сервера (эмуляция `route`).** Очередь создана обрывом `PUT`; затем:
- ответ **400**: «Отправить сейчас» → красный баннер «Сервер не принял: Некорректные данные тренировки (QA 400). Тренировка осталась на устройстве.», метка и запись остаются, D1 = 0; **40 с ожидания — ни одного повтора** (молча не повторяется); после перезагрузки баннер, метка и ошибка на месте, повторов нет;
- ответ **409**: то же (текст причины в баннере, запись в очереди, D1 = 0);
- ответ **503** (повторяемый): очередь цела, D1 = 0 (но см. QA-R03-09);
- сервер снова принимает: «Отправить сейчас» → очередь пуста, метка и баннер ушли, D1 = 1.
- Отказ при самом «Завершить» (не из очереди): 400 → экран тренировки остаётся, ошибка «Некорректные данные…», черновик цел, в очередь не попало; 409 → диалог «Версии тренировки разошлись… Скачать мой черновик / Создать отдельную копию», черновик цел, D1 не менялась.
- Сессия умерла посреди работы (`q3b`): очередь в `localStorage`, `cookie` стёрты, «Отправить сейчас» → экран входа (ошибкой «Сервер не принял» это не показано), очередь осталась; после входа тем же аккаунтом тренировка ушла сама, на сервере 1 запись.

### 5. QA-R03-08 и очередь на втором аккаунте (cloud-entry, `q3-cloud.mjs`)

Истёкшая сессия = `ctx.clearCookies()` + перезагрузка при доступном сервере.

- **Что остаётся на устройстве на экране входа:** `tyaga-draft-account:<id>` (970 байт), `tyaga-pending-workouts:<id>` (766 байт), `tyaga_sound_muted`. Ни `tyaga-offline:*`, ни `tyaga-bodyweight-*`, ни `tyaga-last-import:*`. То есть QA-R03-08 в части кэшей **FIXED** (раньше оставался `tyaga-bodyweight-sync`). Cache Storage: только `tyaga-shell-*` (оболочка, как раньше).
- **Чужая очередь не уходит под вторым аккаунтом.** Выход А (с очередью+черновиком, через «Выйти») → вход Б: ключей А нет, «Продолжить тренировку» нет, меток нет; за 36 с онлайн Б — **0** запросов `PUT /api/workouts`; в D1 у Б 0 тренировок. Тот же результат, когда сессия А истекла и Б входит поверх без явного выхода: очередь и черновик А стёрты (`purgeOthers`), за 36 с ни одного `PUT`, у Б 0 тренировок.
- **На экране входа без сессии** 35 с: 0 запросов `PUT` (очередь без сессии не шлёт).
- **Свой аккаунт после истечения:** А → очередь → истечение → вход А: очередь возвращается и уходит сама (1 тренировка у А в D1 с `owner_id` = `platform_id` А, у Б 0). Проверено на 390 и 360.
- **Итоговая D1 cloud:** у каждого А по 1 тренировке, у каждого Б по 0.

**Оценка риска остатка.** После истечения сессии на устройстве в открытом виде остаются незавершённая тренировка и очередь (упражнения, веса, повторы; профиля и почты в этих ключах нет), пока тот же человек не войдёт снова или кто-то не войдёт под другим аккаунтом. Через DevTools / XSS на этом origin их можно прочитать. Чужому аккаунту в приложении они не показываются и не отправляются (проверено выше). Вывод инженера (молча терять тренировку при истечении сессии хуже) считаю разумным; риск **низкий–средний** только для общего устройства. Хорошо бы записать это в документацию как сознательное решение (QA-R03-03 остаток); не дефект.
