# Тяга 1.4 — аккаунт, первая тренировка, разминка и Apple Watch

7 октября 2026 года. Цель релиза — рабочий журнал для первой реальной тренировки,
с явными значениями показателей и без расширения интерфейса до сложного тренерского комбайна.

## Аккаунт

Страницы `#/register`, `#/login`, `#/recover`. Почта используется как идентификатор
для входа: отправка и подтверждение почты не реализованы. Есть одноразовый код
восстановления, который показывается только при создании/восстановлении аккаунта.
Профиль хранит имя, почту, вес тела и IANA timezone. Смена пароля требует текущий
пароль и отзывает все прежние сессии; код восстановления после применения заменяется.

`AccountService` хранит солёный PBKDF2-SHA256 hash (100 000 итераций, ограничение
WebCrypto Workers), SHA256 хеши случайных 256-битных токенов сессии и хеши кодов
восстановления. Пароли и токены не входят в экспорт журнала. Сессия действует
30 дней, проверяется сервером при каждом запросе, отзывается при выходе.
Cookie на HTTPS: `__Host-tyaga_session`, `HttpOnly`, `Secure`, `SameSite=Strict`,
`Path=/`, без Domain. Для встроенного Site выдаётся тот же токен в отдельной
`__Host-tyaga_embedded` cookie: HttpOnly, Secure, SameSite=None, Partitioned.
Она изолирована по сайту верхнего уровня; Origin и платформенная привязка
обязательны также для неё. На локальном HTTP — `tyaga_session`, без Secure.
Различающиеся дубли одной cookie отвергаются. Все изменения, включая логин,
проверяют Origin и JSON Content-Type. Попытки входа/регистрации/восстановления
ограничены в D1: 15 попыток за 15 минут на доверенную платформенную идентичность.

**Две границы доступа.** Развёрнутый Site остаётся приватным; Sites сначала
аутентифицирует владельца, приложение дополнительно требует свою сессию.
Один профиль Тяги привязан к одной платформенной идентичности. На другом устройстве
используются тот же аккаунт Sites и почта/пароль Тяги. Поэтому прежние owner_id,
тренировки, программы и избранное не меняются при регистрации. Это не общий
публичный SaaS-вход для людей без доступа к приватному Site. При самостоятельном
хостинге нужно проверять/вставлять платформенную идентичность на доверенном ingress;
внешний заголовок нельзя принимать от клиента. `server/local.ts` только для разработки.

Черновик хранится отдельно по ID аккаунта. Выход не удаляет черновик; повторный
вход возвращает его. Старый не привязанный черновик переносится только явным
действием пользователя; исходник удаляется лишь после успешного сохранения копии.

## Разминка и первая аналитика

`SessionReport` разделяет рабочие и разминочные подходы, внешний тоннаж и
прямое/помогающее участие. Сразу после сохранения появляется отчёт; тот же отчёт
доступен в деталях истории после перезагрузки. Главный тоннаж и график включают
все выполненные подходы свободных весов, включая разминку. Недельное покрытие
и e1RM сохраняют рабочую семантику. Значения стеков, помощь и масса тела не
суммируются с килограммами свободных весов.

`WarmupPlanner` создаёт редактируемую заготовку 40/60/80% записанного рабочего
веса, с 8/5/3 повторениями, неизвестным RIR и невыполненными подходами. Для 50 кг
это 20/30/40 кг. Это удобство записи, **не персональный протокол подготовки**.
Разминочная работа не получает выдуманный коэффициент «стимула роста».
Для завершения по-прежнему нужен хотя бы один выполненный рабочий подход.

Основание: Ribeiro et al., 2020, DOI
[10.3390/ijerph17186882](https://pmc.ncbi.nlm.nih.gov/articles/PMC7558980/) — полный текст;
Viveiros et al., 2024, DOI
[10.1016/j.jbmt.2024.08.004](https://pubmed.ncbi.nlm.nih.gov/39593476/) — метаданные
и выдержки абстракта/страницы издателя. Эти исследования описывают острые
показатели последующих рабочих подходов, не устанавливают проценты гипертрофии
или универсальный тренировочный объём от разминки.

## wger и свои тренажёры

Новый неизменяемый релиз `catalog-v3-reviewed.json` содержит 918 упражнений,
26 явных редакционных проверок по источникам. Для изменённых записей выпущены
новые content IDs; обе старые версии остаются доступными в архиве. Проверяются
функциональные роли и правило записи конкретного движения. Это работа с помощью
ИИ по функциональной анатомии и указанным исследованиям, **без независимой
сертификации экспертом**. Не проверенные 892 записи не заполняют карту мышц.

Свой тренажёр может использовать базовое движение каталога Тяги, выбранное
владельцем. Его подходы участвуют в карте с происхождением `user-declared`,
e1RM отключён. Простые поисковые теги без базового движения не превращаются
в мышечную аналитику. Изменение базы движения создаёт новый immutable ID.
Резервные копии сохраняют этот выбор.

## Apple Watch / Apple Health

**Реализован импорт, не живая синхронизация.** Во время тренировки пользователь
включает традиционную или функциональную силовую тренировку на часах. После
синхронизации с iPhone: Здоровье → профиль → Экспортировать все данные → Файлы.
В деталях тренировки Тяги можно выбрать `export.xml` или ZIP и конкретную
силовую тренировку за тот же календарный день в её timezone.

`AppleHealthImport` и отдельный Web Worker потоково читают XML; ZIP разбирается
fflate, XML — saxes. Файл никогда не отправляется на сервер. Остаются только
силовые сессии нужного дня и до 20 000 показаний пульса вокруг него; остальная
история здоровья не сохраняется. Лимиты: ZIP 250 МБ, XML 1 ГБ. Можно отменить
обработку. Сервер сохраняет только выбранное резюме: время, источник, вид
тренировки, калории и пульс, с обычной revision-защитой. Время журнала и подходы
не заменяются данными часов; резюме можно удалить или заменить.

Приоритет имеют WorkoutStatistics. Без них средний пульс — обычное среднее
выборок того же sourceName в интервале тренировки, не непрерывное измерение.
Энергия ActiveEnergyBurned обозначается активной; старое totalEnergyBurned —
«энергия по экспорту». kJ переводятся в kcal. Калории — оценка устройства.
XML-данные загружает пользователь, они не криптографически подтверждены Apple.
Резюме сохраняется в JSON-экспорте/восстановлении Тяги.

Основание: [Apple — экспорт XML](https://support.apple.com/guide/iphone/share-your-health-data-iph5ede58c3d/ios),
[Apple — HealthKit](https://developer.apple.com/documentation/healthkit/authorizing-access-to-health-data).
Для автоматического чтения и записи HealthKit нужна нативная iOS/watchOS-часть
с разрешениями пользователя. Сайт её не заменяет.

## Повторная проверка OpenGym

Проверен main `31c6795b40fb54130192b5016d7dc29e9f457d30` (6 октября 2026).
Изучены [api/server.js](https://github.com/DuarteSantos8/openGym/blob/31c6795b40fb54130192b5016d7dc29e9f457d30/api/server.js)
и [api/password.js](https://github.com/DuarteSantos8/openGym/blob/31c6795b40fb54130192b5016d7dc29e9f457d30/api/password.js),
структура тестов, хранилища и профилей. OpenGym использует Node/filesystem,
atomic rename для `db.json` и отдельных `state-<uid>.json`, passkeys и опциональный
scrypt-вход. Тяга остаётся Worker/D1 с атомарными SQL-версиями, cookie-сессиями
и небольшими предметными классами. Идеи разделения профилей, проверки Origin,
отзыва сессий и истории реализованы самостоятельно. AGPL-исходники не переносились.

Профиль, программы, избранное и страницы каталога читаются D1 batch, чтобы
получать согласованные снимки и не запускать параллельные read RPC внутри одной
операции. Это также исправляет найденную при браузерной проверке нестабильность
чтения после удаления личного упражнения.
