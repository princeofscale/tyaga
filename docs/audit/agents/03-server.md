## Находки

### 1. [HIGH] CSP блокирует blob: — анализ техники по видео не работает в проде
- Где: `server/index.ts:482` (политика) ↔ `src/components/PoseAnalysisPanel.tsx:110,116-118`
- Что: политика `default-src 'self'; ... img-src 'self' data:` не содержит `media-src`/`blob:`, значит для `<video>` действует `default-src 'self'`. Компонент подставляет `src={URL.createObjectURL(file)}`, т.е. `blob:https://…`. Chrome/Firefox такой источник при `'self'` не считают своим.
- Почему плохо: предпросмотр и сам анализ видео («Видео подхода» → PoseVideoAnalysis) падают на `onError` → пользователь видит «Браузер не смог прочитать этот формат видео». В e2e на vite preview заголовка CSP нет, поэтому регрессия не ловится (ровно тот же класс, что описан в комментарии 478-481 для MediaPipe).
- Как чинить: добавить в политику `media-src 'self' blob:` (и на будущее `img-src 'self' data: blob:`), проверить вживую на Worker-сборке.
- Уверенность: подтверждено чтением (код + текст политики); поведение браузера для `blob:` под `'self'` — стандартное исключение.

### 2. [HIGH] POST /api/sync/apply пишет payload без валидации
- Где: `server/SyncService.ts:164-195` (parseDoc), запись — `SyncService.ts:32,39,46,53`
- Что: для `kind=workout` проверяется только `payload.programDate` (193), для `routine` — периодизация (184-192). Остальной payload (exercises/sets/notes/date) не проходит `validWorkout`/`validRoutine`, а колонки `date`/`revision` берутся из клиента как свободные `str(source.date, 400000)` / `num(...,0,2147483646)` (176-177). В отличие от `PUT /api/workouts` (`server/index.ts:355-388`), где работает полная валидация и CAS по revision.
- Почему плохо: любое устройство (или баг клиента) может положить в журнал тренировку произвольной формы: `{"exercises":[]}`, дата «сегодня_потом», revision не по порядку. `/api/data` сортирует по `date` — битая строка ломает порядок; битый payload ломает рендер на всех устройствах пользователя (данные — единственная копия, облако перезапишет локальные).
- Как чинить: в `parseDoc` для workout/routine прогонять `validWorkout(payload,{allowIncomplete:true})`/`validRoutine` (или хотя бы проверять `isCalendarDate(date)`, целочисленный revision, наличие exercises) и ограничить payload ~100 КБ.
- Уверенность: подтверждено чтением.

### 3. [MED] «Свежесть» документа в sync сравнивается лексикографически, а формат версии неканонический
- Где: `server/SyncService.ts:64` (регэксп версии), `:123` (`d.versionAt > current`), `:134`; формат серверных меток — `drizzle/0006_sync.sql:28` (`%f` → 3 знака)
- Что: `VERSION` допускает `.d{1,3}` дробной части, а сравнение — строковое. `2026-11-24T10:00:00.500Z` < `2026-11-24T10:00:00Z`, потому что `'.'`(0x2E) < `'Z'`(0x5A). Android-клиент (`cloud.ts:1-3` — Bearer, Capacitor) через `Instant.toString()` как раз выдаёт метку без дробной части при точной секунде.
- Почему плохо: правка, сделанная в ту же секунду с миллисекундами, считается «старее» и молча отбрасывается (`skipped`) → потеря правки без ошибки на клиенте. Окно узкое (внутри одной секунды), но диагностировать невозможно.
- Как чинить: канонизировать `versionAt = new Date(versionAt).toISOString()` на входе (тогда всегда 3 знака) либо сравнивать `Date.parse`, а не строки; регэксп сузить до `.\d{3}`.
- Уверенность: подтверждено чтением + проверка лексикографического порядка ('.'<'Z').

### 4. [MED] Кривой percent-encoding в пути → 503 «Не удалось обратиться к хранилищу»
- Где: `server/index.ts:444-460` (catch), сайты декодирования: 78, 85, 117, 122, 128, 140, 162, 207, 248, 414
- Что: `decodeURIComponent` бросает `URIError` на битой последовательности (например `/api/workouts/%`, `/api/workouts/%E0%A4%A`); `new URL` такие пути сохраняет как есть. `catch` разбирает только `AuthError`, `InputError`, `SyntaxError`, всё прочее → 503 + `console.error("Workout storage request failed")` (449-452).
- Почему плохо: клиентская опечатка в URL (или чужой бот) выглядит как падение хранилища: 503, «Форма остаётся открытой — попробуйте ещё раз» и засорение логов; ретраи клиента множатся. Правильный ответ — 400.
- Как чинить: добавить `if (error instanceof URIError) return json({error:"Некорректный адрес"},400)` перед общим catch, либо обернуть все `decodeURIComponent` в один `pathId()`-хелпер.
- Уверенность: подтверждено чтением; воспроизведение: `DELETE /api/workouts/%` с валидной сессией + JSON-телом.

### 5. [MED] OPTIONS не обработан в основном роутере (только кросс-доменная ветка cloud.ts)
- Где: `server/index.ts:58-67`, `server/cloud.ts:112-114`
- Что: `OPTIONS` не входит в `["GET","HEAD"]`, поэтому требует `Origin === url.origin` и `Content-Type: application/json`; у preflight тела и Content-Type нет → 415 «Требуется JSON». В `cloud.ts` preflight обслуживается только если `Origin` присутствует и НЕ равен `url.origin` (113-114); OPTIONS без Origin или с тем же Origin уходит в `handleApi` → 415.
- Почему плохо: любой нестандартный клиент (нативный HTTP, WebView с `Origin: null`, корпоративный прокси, переписавший Origin) получает 415 вместо 204; диагностика CORS превращается в квест. Для браузера с кросс-доменным API сейчас спасает только ветка cloud.ts.
- Как чинить: в начале `handleApi` (или в `fetch` обоих входов) отвечать `204` c CORS-заголовками на `OPTIONS` до проверок Origin/Content-Type; в `cloud.ts` убрать зависимость от `Origin`.
- Уверенность: подтверждено чтением; воспроизведение: `curl -X OPTIONS -H 'Origin: http://localhost:8787' http://localhost:8787/api/data`.

### 6. [MED] Тело запроса читается в память целиком до проверки размера
- Где: `server/index.ts:462-466`; также `cloud.ts:73` (повторное `request.text()` для всех не-GET) и `AccountService.ts:232-233` (третий read для auth-путей)
- Что: `const body = await request.text(); if (body.length > 500000) throw new InputError(...)` — лимит применяется ПОСЛЕ буферизации всего тела; `length` считается в UTF-16 символах, не в байтах. `Content-Length`/потоковое ограничение не используются. В облачном входе тело читается в `cloud.ts:73`, затем ещё раз внутри `handleApi`/`AccountService.handle`.
- Почему плохо: один POST на 100 МБ съедает память изолятора (лимит Workers 128 МБ) до того, как сработает 400; несколько параллельных — 503 для всех. Двойное/тройное чтение удваивает стоимость каждого запроса.
- Как чинить: проверять `Content-Length` до чтения, ограничивать поток (reader + счётчик), поднять один разобранный body в параметр `handleApi(request, env, body)` и не читать повторно.
- Уверенность: подтверждено чтением.

### 13. [LOW] Повторный logout отдаёт 401, а не 200

### 16. [LOW] Второй `json()` в cloud.ts теряет защитные заголовки; CORS навешивается двумя путями
- Где: `server/cloud.ts:20-21` против `server/index.ts:34-42`
- Что: локальный `json()` (используется для 429 лимита и 409 «почта занята», 76/87) отдаёт только Content-Type — без `Cache-Control: no-store` и `X-Content-Type-Options: nosniff`, которые есть у основного хелпера. CORS-карта применяется и в preflight-ветке (114), и в обычной (117), хотя обе возвращают одни и те же заголовки; preflight не отдаёт `Vary: Origin`.
- Почему плохо: ответы об ошибках auth кешируются промежуточными слоями иначе, чем остальные; расхождение заголовков между двумя хелперами — источник будущих регрессий (например, забыть no-store на новом ответе).
- Как чинить: один общий `json()`/набор заголовков для обоих входов; CORS вешать одной функцией `withCors(response)` на всех выходах `cloud.ts`.
- Уверенность: подтверждено чтением.

### 17. [INFO] PBKDF2 600k без `limits.cpu_ms` в конфиге Worker
- Где: `server/AccountService.ts:36`, `wrangler.production.jsonc` (секции `limits` нет)
- Что: каждый вход/регистрация/восстановление/смена пароля считает PBKDF2-SHA256 на 600 000 итераций (плюс повторное хеширование при апгрейде legacy). CPU-лимит в конфиге не задан и тариф неизвестен.
- Почему плохо: на Free-плане (10 мс CPU) такой вход стабильно падает 1102 «exceeded CPU», т.е. авторизация не работает вовсе; на Paid — съедает заметную долю CPU-бюджета каждого логина.
- Как чинить: зафиксировать тариф/лимит в конфиге (`limits: { cpu_ms: 50 }` требует Paid), либо снизить итерации до значений, проверенных на реальном деплое, и замерить.
- Уверенность: гипотеза (зависит от тарифа; в репозитории тариф не виден).

### 18. [INFO] `auth_limits` не чистится: по строке на каждый IP/аккаунт навсегда
- Где: `server/cloud.ts:46-53`, `server/AccountService.ts:162-175`
- Что: `noteIpFailure` вставляет строку `ip:<CF-Connecting-IP>` и больше никогда её не удаляет (успех счётчик не сбрасывает — так задумано, 34-37); `clearFailures` чистит только ключ аккаунта.
- Почему плохо: таблица монотонно растёт (ботнеты/сканеры = уникальные IP), лишние строки и мусорные счётчики остаются навсегда.
- Как чинить: удалять строки со `window_start < now-24h` при записи (или периодически).
- Уверенность: подтверждено чтением.

### 19. [INFO] cloud.ts принимает непрефиксную cookie `tyaga_session` — заготовка для фиксации сессии на своём домене
- Где: `server/cloud.ts:26-30` против `server/AccountService.ts:102-111`
- Что: `sessionToken` ищет `__Host-tyaga_session` ИЛИ `tyaga_session` (без префикса), а `AccountService.token` на https читает только `__Host-…`
- Почему плохо: при переезде на собственный домен соседний поддомен сможет выставить `tyaga_session` (Domain=…) и подсунуть чужой токен; сейчас такой запрос всё равно упадёт на `require` (несогласованные имена), т.е. получится непонятная 401, а не захват — но сама конструкция лишняя.
- Как чинить: в `sessionToken` оставить только `__Host-tyaga_session` (и `__Host-tyaga_embedded` при необходимости).
- Уверенность: подтверждено чтением; эксплуатация сейчас не подтверждена.

## Что проверил и НЕ подтвердилось

- **SQL-инъекции.** Все IN-списки собираются как `?`-плейсхолдеры, динамические ORDER BY/фрагменты — константы: `ExerciseRepository.ts:182,198,208,210,255`, `HistoryImportService.ts:89,295,328,412,460`, `ImportReceiptService.ts:38,84`, `ProductRepository.ts:54`, `SharedProgramRepository.ts:109`, `MachineRepository.ts:12` (тернарник по булеву), `LiveRoomService.ts:24,108` (в строку подставляется только константный guard). Пользовательские значения везде через `.bind`.
- **Разбор внешних CSV/HTML/zip на сервере.** Импорт принимает только JSON (`HistoryImportService.ts:32-42`, `format` ∈ strong/hevy/fitnotes/tyaga), парсинг архивов и CSV живёт на клиенте (`fflate`, `saxes` в `package.json`). Zip-bomb и размер CSV — клиентский риск; серверный предел — тело 500 КБ (`server/index.ts:464`) и 30 тренировок/запрос.
- **Подделка `oai-authenticated-user-id`.** В cloud/local/device входах заголовок перезаписывается (`cloud.ts:94`, `local.ts:6`, `src/device/localBackend.ts:70`); тесты это фиксируют (`tests/sync.test.ts:83`). Открытый вопрос только про `dist/server` — вынесен в находку 11.
- **NaN/Infinity/числа-строками/отрицательный вес.** `num()` требует `typeof number` + `Number.isFinite` + границы (`validation.ts:30-40`); вес `num(s.weight,0,1000)` — отрицательный отбивается (197); строки вместо чисел отбиваются типом.
- **XSS в имени/заметках.** Сервер тексты не санитизирует, но в `src/` нет ни `dangerouslySetInnerHTML`, ни `innerHTML`, ни инлайновых `<style>` (grep = 0), React экранирует; хранимый XSS не складывается.
- **Prototype pollution через ключи JSON.** Валидация не делает merge пользовательского объекта в прототип: `object()` только проверяет форму (`validation.ts:20-24`), `validSettings` собирает цели через `Object.fromEntries` по списку `MUSCLES` (402-404), поля выбираются поимённо. Путь `__proto__`/constructor не найден.
- **Path traversal / двойные слэши / method override.** `new URL` нормализует `..` и не схлопывает `//` (такой путь просто не матчится и уходит в ASSETS), файловой системы в обработчиках нет; override-заголовка нигде нет. `%2F` внутри id декодируется уже после матчинга и уходит в параметризованный SQL — безобидно.
- **`style-src 'self'` ломает inline-стили React.** Не подтвердилось: React ставит style через CSSOM, инлайновых `<style>` в сборке нет; для атрибутов `style` CSP не применяется. Проблема только с `blob:` (находка 1).
- **Отсутствие rate limiting на логин/регистрацию.** Не подтвердилось: лимит 15 отказов/15 мин на аккаунт (`AccountService.ts:180-183`, вызывается до сверки пароля) плюс 30/15 мин на IP в облаке (`cloud.ts:75-76`), успех сбрасывает счётчик аккаунта.
- **Бесконечный рост `last_seen_at`.** Не подтвердилось: обновление не чаще `SESSION_TOUCH_MS = 5 мин` (`AccountService.ts:13,121-123`), да и то одним UPDATE.
- **Session fixation.** Не подтвердилось: каждый вход/восстановление/смена пароля создаёт новый случайный токен (`newSession`, 149-160), старый не переиспользуется; отзыв работает (212-231, 297-306).
- **Утечка чужого через sync (обход owner_id).** Не подтвердилось: `owner_id` везде в WHERE/bind, апсерты с `WHERE <table>.owner_id = excluded.owner_id` (`SyncService.ts:32,39,46`), отдельная проверка владельца для single-PK таблиц (65-69,119-121); чужие строки не перезаписываются.
